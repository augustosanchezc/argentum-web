1. Decisiones asumidas

Las 7 decisiones que estaban abiertas se cerraron con asunciones para no bloquear la planificación. Todas son revisables antes del fin de la Fase 0.

D-1

Licencia del proyecto

AGPL-3.0 desde el día 1
Elimina ambigüedad legal con los repos de referencia. Coherente con la cultura del juego.
⚠ Asunción — revisable
D-2

Versión de AO objetivo

Clónico de 0.13.3 con balance propio
Versión con mayor documentación de-facto. AO20 agrega complejidad sin ventaja inmediata.
⚠ Asunción — revisable
D-3

Alcance funcional del MVP

Caminar + chat + PvP, sin inventario ni NPCs
Valida el stack con el menor scope. Inventario y NPCs entran en Fase 3.
⚠ Asunción — revisable
D-4

Compatibilidad con clientes

No — WebSocket binario propio
Trabaja nativo en navegador sin proxy TCP. El cliente propio es parte del diferencial.
⚠ Asunción — revisable
D-5

Modelo de comunidad

Servidor único oficial
Facilita moderación, balance y coherencia. Multi-server queda para Fase 5+.
⚠ Asunción — revisable
D-6

Monetización

Donaciones voluntarias (F2P puro)
Coherente con AGPL. Sin sistema de tienda en MVP. Pase cosmético se evalúa en Fase 4.
⚠ Asunción — revisable
D-7

Mobile-first vs desktop-first

Desktop-first; táctil paralelo desde Fase 2
Grilla y UI densa difícil de adaptar en mobile sin rediseño. Validamos mobile con comunidad.
⚠ Asunción — revisable

Fase 0 — Setup y decisiones

Sprint 1 · 2026-06-23 → 2026-07-04 · Sentar el entorno: repo, licencia, Docker, ADRs.
▾

Objetivo: tener el entorno de desarrollo funcionando, el repositorio inicializado con licencia y estructura acordada, y los primeros ADRs escritos para que backend y frontend puedan arrancar sin ambigüedades.

Criterios de aceptación

  • Repositorio Git con LICENSE AGPL-3.0, .gitignore y estructura monorepo.
  • README con instalación y guía de contribución.
  • Programas de PROGRAMAS-NECESARIOS.md instalados y verificados.
  • Docker Compose levanta PostgreSQL + Redis sin errores.
  • ADR-001 (licencia), ADR-002 (stack), ADR-003 (protocolo) mergeados.
  • Borrador de docs/protocol.md con paquetes de login y movimiento.
  • docs/design-system.md con paleta, tipografía y principios de UI.

Entregables por agente

  • backend Monorepo (packages/server, packages/shared), docker-compose.yml, esquema SQL inicial, borrador docs/protocol.md.
  • frontend Scaffolding packages/client con Vite + PixiJS v8 + TS, docs/design-system.md, paleta inspirada en AO clásico.
  • PM Este roadmap, backlog.md, risks.md, ADR-001 a ADR-003, definition-of-done.md.

Hitos visibles

  • Semana 1: repo público, licencia y estructura, Docker Compose funcional.
  • Semana 2: primer npx vite y primer node server/index.ts sin errores; ADRs mergeados.

Fase 1 — Prototipo de red

Sprints 2-3 · 2026-07-07 → 2026-07-31 · Login + WebSocket + un personaje moviéndose en un mapa.
▾

Objetivo: un personaje puede conectarse desde el navegador, autenticarse con usuario y contraseña, ver un mapa estático y moverse en tiempo real. Sin combate, sin chat completo, sin NPCs. Solo validar que el stack de red funciona de punta a punta.

Criterios de aceptación

  • Cliente web carga en Chromium y Firefox sin errores críticos.
  • Login HTTP con JWT: registro, inicio de sesión, selección de personaje.
  • WebSocket establecido con token validado.
  • Personaje aparece en el mapa con sprite y posición correctos.
  • Movimiento WASD / flechas con servidor autoritativo.
  • Dos clientes ven moverse al otro (latencia < 200ms en LAN).
  • Mapa 50×50 cargado desde servidor (JSON/Tiled).
  • Posición persistida al desconectarse.

Entregables por agente

  • backend Servidor WebSocket, game loop 100ms, módulos auth / session / movement / map-loader; paquetes LOGIN, MOVE, DISCONNECT, MAP_DATA, ENTITY_UPDATE.
  • frontend Canvas PixiJS con tilemap, sprite animado (idle + walk 4 direcciones), input WASD, pantalla de login y selección de personaje.

Hitos visibles

  • Fin Sprint 2: login funcional, WebSocket conectando, tile en pantalla.
  • Fin Sprint 3: dos jugadores viéndose moverse en el mismo mapa.

Riesgos en esta fase

RiesgoProb.ImpactoMitigación
Drift entre spec y protocolo implementadoAltaAltodocs/protocol.md como fuente de verdad; PR no mergeable sin spec actualizada
Latencia WebSocket inaceptable con wsBajaMedioEvaluar uWebSockets.js si supera 150ms en LAN
Sprites del AO clásico sin licencia claraAltaMedioPlaceholder libres (OpenGameArt); decisión final con el usuario

Fase 2 — Slice vertical jugable

Sprints 4-5 · 2026-08-03 → 2026-08-28 · Caminar + chat + combate PvP en un mapa. Primera demo filmable.
▾

Objetivo: el juego es jugable de forma mínima — caminar, chatear con otros jugadores y golpear con ataque cuerpo a cuerpo, con persistencia de stats y muerte/respawn simple. Es el primer momento en que el proyecto se puede mostrar a jugadores externos.

Criterios de aceptación

  • Chat global funcional con nombre, timestamp y scroll.
  • Ataque cuerpo a cuerpo: animación, daño en servidor, barra de vida visible.
  • Stats persistidos en PostgreSQL: HP, MaxHP, nivel 1 fijo.
  • Muerte y respawn en punto fijo del mapa.
  • HUD mínimo: barra HP, nombre, lista de online.
  • Servidor rechaza movimientos y ataques inválidos.
  • Conexión a sesión jugable < 10 s en LAN.
  • Log de errores funcionando (Winston o Pino).

Entregables por agente

  • backend Módulos chat, combat, stats, death-respawn; paquetes CHAT_MSG, ATTACK, DAMAGE, DEATH, RESPAWN; migraciones SQL; logging.
  • frontend HUD con barra HP, chat overlay, animación de ataque, número flotante de daño, pantalla de death/respawn; primer pase de controles táctiles.

Hitos visibles

  • Fin Sprint 4: chat funcional, stats persistidos.
  • Fin Sprint 5: combate PvP básico jugable, demo interna filmable.

Riesgos en esta fase

RiesgoProb.ImpactoMitigación
Balance de daño inestableAltaBajoFórmulas hardcodeadas simples; balance real en Fase 3
Anti-cheat complejo → scope creepMediaMedioMVP: solo validación de posición y cooldown
Performance del loop con chat + combateBajaAltoLoad test con k6 antes de cerrar fase (20 conexiones)

Fase 3 — MVP cerrado

Sprints 6-8 · 2026-09-01 → 2026-09-25 · NPCs + inventario + items + experiencia. Loop de gameplay completo.
▾

Objetivo: experiencia de juego completa mínima — NPCs con IA básica, inventario, items lootables, sistema de experiencia y niveles, comercio con NPCs. El juego tiene un loop cerrado: matar → lootear → subir de nivel → volverse más fuerte.

Criterios de aceptación

  • 3 tipos de NPC: hostil, neutro, comerciante.
  • Inventario persistido: recoger, equipar, soltar.
  • 5 items base: espada, escudo, poción HP, oro, trofeo.
  • Comercio con NPC: ventana de tienda, compra/venta.
  • Sistema de experiencia, niveles 1-10.
  • NPCs reaparecen en posición original.
  • Servidor soporta 50 conexiones simultáneas.
  • docs/architecture.md actualizado.

Entregables por agente

  • backend Módulos npc-ai, inventory, items, experience, shop; spawners; migraciones SQL; prueba de carga k6.
  • frontend Ventana de inventario drag-and-drop, ventana de tienda, barra XP, indicadores de nivel, sprites placeholder de NPCs.

Hitos visibles

  • Fin Sprint 6: NPC hostil funcional, drops de items.
  • Fin Sprint 7: inventario completo persistido, comercio con NPC.
  • Fin Sprint 8: niveles 1-10, prueba de carga superada, cierre del MVP.

Riesgos en esta fase

RiesgoProb.ImpactoMitigación
IA de NPCs más compleja de lo estimadoMediaMedioPathfinding A* simple; comportamientos avanzados → backlog
Inventario drag-and-drop en mobileMediaBajoMobile en Fase 3 es best-effort; firme es desktop
Scope creep: nuevas clases / hechizosAltaAltoSolo los 5 items base; el resto va al backlog de Fase 5

Fase 4 — Beta pública

Sprints 9-12 · 2026-09-29 → 2026-10-23 · Múltiples mapas + banco + party + comercio P2P + infra prod + observabilidad.
▾

Objetivo: el servidor está accesible en internet, con múltiples mapas, teletransportes, banco, party, comercio jugador-jugador, observabilidad de producción y canal de feedback. Se invitan los primeros jugadores externos.

Criterios de aceptación

  • 3+ mapas con transiciones (portales).
  • Banco de items persistido por personaje.
  • Party de hasta 5 jugadores; no daño entre aliados.
  • Comercio P2P seguro (commit/cancel).
  • VPS con dominio, HTTPS y WSS.
  • Grafana + Prometheus + alertas de caída.
  • Sentry en cliente y servidor.
  • Discord con #bugs y #feedback.
  • 200 conexiones simultáneas.
  • Política de privacidad y términos publicados.

Entregables por agente

  • backend Sistema multi-mapa, banco, party, comercio seguro, despliegue VPS (Caddy + Docker), Prometheus + Grafana, Sentry server-side.
  • frontend UI multi-mapa, ventana de banco, UI de party (HP aliados), ventana de comercio seguro, Sentry client-side, mejoras UX por feedback.

Hitos visibles

  • Fin Sprint 9: multi-mapa funcional.
  • Fin Sprint 10: banco y party.
  • Fin Sprint 11: servidor en producción, observabilidad activa.
  • Fin Sprint 12: primera invitación a externos, Discord abierto.

Riesgos en esta fase

RiesgoProb.ImpactoMitigación
Bugs de seguridad en comercio P2PMediaAltoCommit/rollback atómico; revisión de código obligatoria
Exploits de duplicación de items (dupe)AltaAltoTransacciones SQL atómicas + logs auditables
Costos de VPS subestimadosBajaMedioEmpezar con 4 vCPU / 8 GB; escalar vertical

Dependencias transversales

  • docs/protocol.md es interfaz entre backend y frontend en cada fase. Cualquier cambio requiere actualización sincronizada de ambos lados.
  • Assets gráficos no bloquean lógica de servidor, pero sí bloquean cierre de fases en el lado frontend. Placeholders libres desbloquean el desarrollo.
  • Infra de producción (VPS) no es necesaria hasta Fase 4, pero el contrato debe iniciarse durante Fase 3.

5. Definition of Done por fase

Fase 0 — Setup

Repo público con licencia; Docker Compose funcional; ADRs 1-3 mergeados; todos los programas verificados.

Fase 1 — Proto red

Dos navegadores distintos conectados simultáneamente, dos personajes visibles moviéndose, posición persistida al desconectar.

Fase 2 — Slice jugable

Sesión de 5 min grabada: un jugador mata a otro, chatea, y el perdedor reaparece. Sin bugs críticos.

Fase 3 — MVP

Loop completo: personaje nivel 1 → mata NPC → lootea item → compra en tienda → sube a nivel 2. Probado con 50 conexiones.

Fase 4 — Beta

100 jugadores reales en Discord; servidor estable 24/7 con uptime > 99% en las primeras 2 semanas; canal de bugs activo.

6. Costos e infraestructura

Resumen ejecutivo. Detalle completo en docs/costos-e-infraestructura.md: comparativa de proveedores, alternativas free vs paid, riesgos económicos, y método de pago desde Argentina.

Headline: el proyecto se puede llevar hasta la Beta pública gastando ~USD 130 totales, manteniéndose en USD 0 durante Fases 0-3. El costo está dominado por dos decisiones: assets gráficos (libres = USD 0 vs comisión = USD 1.000-3.000) y VPS de producción (~USD 15-25/mes desde Fase 4).

7. Preguntas para el usuario

Estas decisiones afectan el alcance y requieren confirmación antes de que sus fases inicien. Ordenadas por urgencia.

Urgentes — antes de fin de Fase 0 (Sprint 1)

⚑ Urgente

D-1 — Licencia

¿Confirmás AGPL-3.0 como licencia del proyecto? Si preferís privado o MIT, el alcance del uso de repos de referencia cambia significativamente.

⚑ Urgente

D-2 — Versión objetivo

¿Clon fiel de AO 0.13.3 o más libertad para rebalancear desde el principio? Afecta el diseño de fórmulas de combate desde Fase 2.

⚑ Urgente

Assets gráficos (R-02)

¿Sprites clásicos de AO asumiendo riesgo, contratar pixel-art original, o empezar con assets libres? Define si el frontend-designer necesita presupuesto.

Importantes — antes de Fase 2

◆ Importante

D-7 — Mobile

¿Mobile es requisito de negocio para la Beta, o puede ir post-Beta? Si es requisito, frontend empieza diseño táctil desde Fase 1.

◆ Importante

D-6 — Monetización

¿Solo donaciones, o algún modelo cosmético para la Beta? Afecta qué datos persistir y si hace falta integración de pagos.

Puede esperar — hasta Fase 3

○ Diferido

D-5 — Multi-servidor

¿Experiencia única (servidor oficial) o que cualquiera pueda levantar el suyo? Afecta arquitectura de Fase 4+.
